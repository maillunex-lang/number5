# PROFILE-01 · Профиль игрока, витрина, косметика и приватность

**Дата:** 2026-11-20 · **Формат:** самостоятельное подробное ТЗ для Cursor

## Общий контракт проекта
- Проект: Lunex AFK «Башкортостан: Разлом эпох»; репозиторий `maillunex-lang/number5`, ветка `main`; вертикальный Godot 4.7.2, Android и планируемый веб/PWA; авторитетный Go/PostgreSQL и Lunex Admin Studio.
- Канон: 6 глав, 180 этапов `CH01-01`…`CH06-30`; 45 героев `H01`…`H45`, фракции `F01`…`F06`, редкости N/R/SR/SSR/UR. Не добавлять новых героев и риги без отдельного решения.
- Единый дневной сброс: **06:00 Europe/Moscow**, недельный: понедельник 06:00 МСК. Время и награды определяет сервер, не телефон.
- Единый кошелёк/инвентарь: `gold`, `diamonds`, `hero_xp`, `essence`, `summon_scroll`, `faction_scroll`, `cosmetic_token`, `afk_hour`, `skill_book`, `ore`, `boss_core`, `set_pattern`, `guild_token` по существующим спецификациям. Не заводить второй баланс.
- ×10 призыва выдаёт **10 результатов за 8 предметов**; событие не должно обойти гача pity или удваивать награды. Дубликат героя = 30 персональных фрагментов.
- Магазин остаётся `VIRTUAL_FREE`: никакого реального платежа, все тестовые начисления серверные, атомарные и с явной маркировкой.
- Ни один экран не меняет утверждённую нижнюю навигацию без аудита `docs/STRUCTURE.md`; адаптация 9:16, safe areas, устройства Android с 6 ГБ RAM.
- **Статус:** проектная спецификация, а не свидетельство внедрения. Баланс ниже предложен для тестирования и хранится в конфигурации. Перед реализацией Cursor сверяет реальные модели, API, контентный manifest и смежные документы, составляет conflict report.

## 1. Смысл и границы
Профиль представляет **аккаунт игрока**, а не отдельного героя. Отображает прогресс, достижения, любимого героя из H01–H45, аватар/рамку/титул, гильдию, показатели и публичную карточку. Данные инвентаря, VIP, email, телефон, платежи и IP по умолчанию **не публичны**. Если уровня аккаунта пока нет, не вводить второй опыт ради профиля: использовать прогресс кампании и достижения.

## 2. Структура личного профиля
| Блок | Данные | Публичность |
|---|---|---|
| Шапка | ник, avatar_id, frame_id, title_id, account_public_id | публично |
| Прогресс | глава, максимальный `CHxx-xx`, количество этапов из 180 | публично по настройке |
| Герои | выбранный Hxx, портрет, звёзды, уровень | публично по настройке |
| Коллекция | число открытых из 45, редкости по категориям | только агрегаты, опционально |
| PvE | этаж Башни (до 120), достижения, рекорды | публично по настройке |
| Гильдия | название, тег, роль | публично по настройке |
| Косметика | аватар, рамка, титул, фон | публично |
| Аккаунт | время регистрации, язык, приватность, безопасность | только владелец |
| Монетизация | VIP, подписки, тестовые покупки | только владелец; скрыто по умолчанию |

## 3. Никнейм и идентификаторы
- `account_id` внутренний UUID, не выводить публично. `public_player_id` короткий случайный ID без персональных данных; не использовать последовательный ID, облегчающий перебор.
- Ник 3–18 символов, Unicode NFC, уникальность после нормализации/casefold, фильтр запрещённых слов и похожих системных имён; отображение без HTML. Первое изменение бесплатно, далее раз в 30 дней бесплатно; не вводить платный rename в MVP.
- Переименование сохраняет все ссылки, гильдию, почту и достижения; журнал старых имён доступен модерации, не другим игрокам.
- `favorite_hero_id` только из открытых H01–H45; при отсутствии героев использовать нейтральную эмблему. Не создавать новых персонажей ради профиля.

## 4. Каталог косметики MVP
- 12 базовых аватаров: 6 эмблем F01–F06, 6 символов глав.
- 8 рамок: 2 стартовые, 2 за кампанию, 2 за Башню, 1 за гильдию, 1 за события. `frame_id` не влияет на боевые параметры.
- 12 титулов: по 2 на каждую главу, открываются за сюжетные достижения.
- 6 фонов профиля: по одной теме на главу, доступны за этап `CHxx-30`.
- Не разрешать произвольные пользовательские картинки/анимированные аватары на MVP. Все предметы из существующего asset manifest или подготовленные статичные иконки.
- Нельзя выбрать неоткрытый cosmetic entitlement, даже если клиент подменил JSON.

## 5. Настройки приватности и безопасность
Переключатели `show_campaign_progress`, `show_hero_showcase`, `show_collection_summary`, `show_pve_records`, `show_guild`. По умолчанию **скрыть коллекцию, героев и PvE-рекорды** до осознанного выбора, а публичными оставить ник, аватар, рамку и титул. Запретить публичный поиск по email/телефону; не показывать точный last_seen. Профиль заблокированного пользователя можно скрывать в чате и поиске; это не удаляет серверные данные.

## 6. Экранные маршруты
`PROFILE_SELF`: шапка, герой-витрина, прогресс, достижения, косметика, настройки. `PROFILE_PUBLIC`: урезанная публичная карточка, кнопки «Посмотреть гильдию», «Пожаловаться», «Заблокировать» (если соответствующие системы подключены). `PROFILE_EDIT`: ник, рамка, титул, аватар, фон, видимость. `PROFILE_HISTORY`: последние достижения и события без финансовых данных. `PROFILE_SECURITY`: выход с устройств и управление сессиями, только если сервер поддерживает. Не обещать несуществующую двухфакторную авторизацию.

## 7. Хранилище, API, события
`player_profiles(account_id PK, public_player_id UNIQUE, nickname, normalized_nickname UNIQUE, avatar_id, frame_id, title_id, background_id, favorite_hero_id, privacy_json, updated_at, version)`; `player_cosmetic_entitlements(account_id, cosmetic_id, source, obtained_at, UNIQUE(account_id,cosmetic_id))`; `profile_change_audit(id, account_id, field, changed_at, actor_id)`. Боевые данные и достижения **не копировать** в профиль: читать агрегаты из существующих таблиц или материализованной проекции.

`GET /api/v1/profile/me`, `PATCH /api/v1/profile/me`, `GET /api/v1/players/{public_player_id}/profile`, `GET /api/v1/profile/me/cosmetics`, `POST /api/v1/profile/me/showcase`. События `profile_updated`, `cosmetic_unlocked`, `player_blocked` (последнее только если есть система блокировок).

## Технические требования, единые для реализации
1. Все выдачи проводить в одной транзакции с существующим wallet/inventory ledger; `source_type`, `source_id`, `account_id`, `period_key`, `config_version`, `idempotency_key` обязательны. Уникальные индексы исключают повторный claim.
2. События публиковать через существующий event bus или transactional outbox: `event_id`, `account_id`, `event_type`, `occurred_at`, `payload`, `schema_version`; обработчики идемпотентны.
3. Клиент не может задавать размер награды, вероятность, завершённость задания, время или чужой `account_id`. GET возвращает серверное состояние и версию конфига; POST проверяет право и состояние.
4. Невыданные награды сохраняются в `pending_claims` или игровой почте; не теряются при сетевой ошибке, переполнении инвентаря или рестарте.
5. Админка: черновик → схема/проверка ссылок → симуляция → публикация версии → откат; audit log с actor, причиной и diff. Тестовые выдачи только в sandbox либо с отдельным разрешением и логом.
6. Автотесты: повтор POST, параллельный POST, неверный account_id, устаревший конфиг, переход через 06:00 МСК, рестарт, отсутствующий ассет, Android 9:16, плохая сеть, неактивный аккаунт.
7. API проектировать как `/api/v1/...`; названия адаптировать к фактическим роутам после аудита, не плодить несовместимые endpoints.

## Порядок работы Cursor
- Фаза 0: read-only аудит репозитория и сверка всех смежных `.md`; отчёт `есть / частично / нет / конфликт`.
- Фаза 1: контентные JSON/валидация/миграции, без ломания текущего manifest.
- Фаза 2: вертикальный UI-срез на реальных игровых данных, без фиктивного онлайна; если backend отсутствует, явная маркировка DEMO.
- Фаза 3: серверные API, транзакции, журналы, таймеры, восстановление.
- Фаза 4: Admin Studio, симулятор баланса, аналитика.
- Фаза 5: QA, нагрузка, локализация, оптимизация и регрессионные тесты.
