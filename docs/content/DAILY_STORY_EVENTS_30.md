# DAILY-STORY-01 · 30 ежедневных сюжетных событий

**Дата:** 2026-11-20 · **Формат:** самостоятельное подробное ТЗ для Cursor

## Общий контракт проекта
- Проект: Lunex AFK «Башкортостан: Разлом эпох»; репозиторий `maillunex-lang/number5`, ветка `main`; вертикальный Godot 4.7.2, Android и планируемый веб/PWA; авторитетный Go/PostgreSQL и Lunex Admin Studio.
- Канон: 6 глав, 180 этапов `CH01-01`…`CH06-30`; 45 героев `H01`…`H45`, фракции `F01`…`F06`, редкости N/R/SR/SSR/UR. Не добавлять новых героев и риги без отдельного решения.
- Единый дневной сброс: **06:00 Europe/Moscow**, недельный: понедельник 06:00 МСК. Время и награды определяет сервер, не телефон.
- Единый кошелёк/инвентарь: `gold`, `diamonds`, `hero_xp`, `essence`, `summon_scroll`, `faction_scroll`, `cosmetic_token`, `afk_hour`, `skill_book`, `ore`, `boss_core`, `set_pattern`, `guild_token` по существующим спецификациям. Не заводить второй баланс.
- ×10 призыва выдаёт **10 результатов за 8 предметов**; событие не должно обойти гача pity или удваивать награды. Дубликат героя = 30 персональных фрагментов.
- Магазин остаётся `VIRTUAL_FREE`: никакого реального платежа, все тестовые начисления серверные, атомарные и с явной маркировкой.
- Ни один экран не меняет утверждённую нижнюю навигацию без аудита `docs/STRUCTURE.md`; адаптация 9:16, safe areas, устройства Android с 6 ГБ RAM.
- **Статус:** проектная спецификация, а не свидетельство внедрения. Баланс ниже предложен для тестирования и хранится в конфигурации. Перед реализацией Cursor сверяет реальные модели, API, контентный manifest и смежные документы, составляет conflict report.

## 1. Суть ежедневных сюжетных событий
Это **короткие интерактивные истории** на 1–3 минуты, связанные с уже существующими шестью главами, без новых героев и новых анимаций. Не путать с глобальными временными ивентами EVENT-01. Событие выдаётся **один раз в игровой день** из доступного пула, после `CH01-10`. Игрок видит 2–3 реплики, делает выбор из двух вариантов и получает небольшую награду; иногда появляется опциональный бой 5v5 с существующими врагами. Выбор не меняет канон кампании и не блокирует прогресс.

## 2. Правила генерации и анти-повторы
- В каждой главе 5 сюжетных карточек, всего **30 стартовых историй**. Карточка доступна после соответствующего `CHxx-01`; не спойлерить ещё не пройденную главу.
- Сервер выбирает одну из доступных карточек, избегая повторов за последние 7 выдач, пока пул позволяет. Выбор детерминирован по `account_id + period_key + content_version`, а не по часам клиента.
- Два варианта ответа: A даёт гарантированную награду, B может запускать короткий бой, но итоговая ожидаемая ценность близка. **Никаких азартных скрытых рулеток** и платного reroll.
- Если бой проигран, дать 50% базового золота и разрешить один повтор без нового сюжета в тот же день. Не расходовать сюжетные 20 полноценных повторных наград кампании.
- При невыполнении до 06:00 МСК событие закрывается, награда не создаётся. При подтверждённом выполнении, но незабранной награде создать почтовое право на 7 дней.
- Сюжетные выборы сохранять для персональной истории, но не менять характеристики героев, принадлежность к фракции или финал кампании.

## 4. Сценарный формат каждой карточки
**Обязательная структура:** `intro` (2–3 реплики), `choice_a` (1 реплика ответа + 1 реакция), `choice_b` (1 реплика + реакция), `battle_intro` (если нужен бой), `outro_a`, `outro_b` (1–2 реплики). В MVP карточки из реестра содержат **сюжетные завязки и развилки**, а не готовые полные диалоги; Cursor должен написать локализованные тексты на основе канона главы и отправить их на редакторское согласование, не выдавая их за утверждённый сюжет.

**JSON карточки:** `id`, `chapter`, `unlock_stage`, `title_key`, `intro_lines`, `choices[{id,text_key,battle_template_id,reward_table_id,outro_lines}]`, `cooldown_policy`, `asset_ids`, `content_version`. `battle_template_id` ссылается на врагов из BESTIARY; не придумывать enemy ID. Для каждого варианта награды фиксированы и публично видны до выбора.

## 5. UI и интеграции
Главная → «Событие дня» → иллюстрация главы, диалоговые облака, два варианта выбора, опциональный бой, награда. В журнале профиля показывать 10 последних историй и выбранные ответы, без влияния на боевую мощь. Событие `daily_story_completed` можно использовать в будущих задачах, но **не начислять pass XP** без явной записи в таблице пропуска.

## 6. PostgreSQL/API/админка
`daily_story_assignments(account_id,period_key,story_id,content_version,status,choice_id,assigned_at,completed_at,reward_grant_id,UNIQUE(account_id,period_key))`; `daily_story_history(account_id,story_id,period_key,choice_id,completed_at)`; `daily_story_battles(battle_instance_id,assignment_id,status)`. `GET /api/v1/daily-story/today`, `POST /api/v1/daily-story/{id}/choose`, `POST /api/v1/daily-story/{id}/claim`, `GET /api/v1/daily-story/history`.

Админка: редактор реплик, 30 карточек, preview локализации, привязки к главам/врагам, проверки достижимости, расписание, симулятор повторов 7/30 дней. Тесты: спойлеры, повтор одного дня, два выбора параллельно, поражение в бою, 06:00, почтовый перенос, несуществующий enemy ID, пустые реплики, пропажа сети, разные аккаунты, старый конфиг.


## Технические требования, единые для реализации
1. Все выдачи проводить в одной транзакции с существующим wallet/inventory ledger; `source_type`, `source_id`, `account_id`, `period_key`, `config_version`, `idempotency_key` обязательны. Уникальные индексы исключают повторный claim.
2. События публиковать через существующий event bus или transactional outbox: `event_id`, `account_id`, `event_type`, `occurred_at`, `payload`, `schema_version`; обработчики идемпотентны.
3. Клиент не может задавать размер награды, вероятность, завершённость задания, время или чужой `account_id`. GET возвращает серверное состояние и версию конфига; POST проверяет право и состояние.
4. Невыданные награды сохраняются в `pending_claims` или игровой почте; не теряются при сетевой ошибке, переполнении инвентаря или рестарте.
5. Админка: черновик → схема/проверка ссылок → симуляция → публикация версии → откат; audit log с actor, причиной и diff. Тестовые выдачи только в sandbox либо с отдельным разрешением и логом.
6. Автотесты: повтор POST, параллельный POST, неверный account_id, устаревший конфиг, переход через 06:00 МСК, рестарт, отсутствующий ассет, Android 9:16, плохая сеть, неактивный аккаунт.
7. API проектировать как `/api/v1/...`; названия адаптировать к фактическим роутам после аудита, не плодить несовместимые endpoints.

## Порядок работы Cursor
- Фаза 0: read-only аудит репозитория и сверка всех смежных `.md`; отчёт `есть / частично / нет / конфликт`.
- Фаза 1: контентные JSON/валидация/миграции, без ломания текущего manifest.
- Фаза 2: вертикальный UI-срез на реальных игровых данных, без фиктивного онлайна; если backend отсутствует, явная маркировка DEMO.
- Фаза 3: серверные API, транзакции, журналы, таймеры, восстановление.
- Фаза 4: Admin Studio, симулятор баланса, аналитика.
- Фаза 5: QA, нагрузка, локализация, оптимизация и регрессионные тесты.
