## 1. Назначение
Игровая почта - **единый надёжный канал** для системных уведомлений и получения отложенных наград. Используется ежедневными заданиями (незабранное при сбросе → письмо на 7 дней), календарём входа, событиями, достижениями, компенсациями, рейдами и сезонным пропуском. Почта **не является** свободной перепиской между игроками; личные сообщения остаются вне MVP.

## 2. Категории и жизненный цикл
| Категория | Пример | Вложения | TTL |
|---|---|---|---|
| `system` | техническое объявление | опционально | 30 дней |
| `reward` | награда события/достижения | да | 30 дней |
| `daily_rollover` | выполненное, не забранное ежедневное задание | да | **7 дней** |
| `calendar_rollover` | доступный, но не забранный вход | да | **7 дней** |
| `compensation` | компенсация сбоя | да | 30 дней |
| `guild` | рейдовая награда, которую нельзя забрать напрямую | да | 7 дней, если предусмотрено GUILD-01 |
| `season` | закрытие сезона | да | 30 дней |

Состояния: `unread` → `read` → `claimed` → `archived`; `expired` и `deleted` - отдельные терминальные состояния. **Чтение не равно получению вложений.** Письмо без вложений может быть архивировано, письмо с вложениями удалять только после claim либо явного подтверждения утраты, в MVP лучше запретить удаление до claim.

## 3. Гарантия доставки и начислений
- **Отправитель - сервер** или уполномоченная админка; клиент не может создавать системные письма.
- Письмо с вложением создаётся как **резервированное право на награду** `reward_grant_id`, а не как повторное начисление. До claim ресурсы не находятся в кошельке, если источник изначально не начислил их напрямую.
- Если источник уже начислил награду, письмо только информационное (`attachment_grant_id = NULL`). Нельзя одновременно зачислить награду и положить её ещё раз во вложение.
- Для `daily_rollover` переносить существующее право на награду в письмо, уникальное `(account_id,source_type,source_id,period_key)`.
- `Claim all`: сервер атомарно забирает только доступные вложения и возвращает receipt для каждого; при ошибке одного письма остальные обрабатываются предсказуемо, с точным отчётом.
- Истечение TTL определяется сервером; пользователь видит точную дату. Удалённое/истёкшее письмо не позволяет получить вложения. Компенсация после истечения - отдельное админское действие с аудитом.
- Лимит UI: последние 200 писем, серверная пагинация по cursor; старые прочитанные письма архивируются. Не удалять письма с невостребованными наградами до срока истечения.

## 4. UI
Главная → конверт с badge непрочитанных (не яркий цвет постоянно). Вкладки `Все`, `Награды`, `Система`; строка: иконка категории, тема, дата, срок, наличие вложений. Просмотр: заголовок, локализованный текст, иконки и количества вложений, `Забрать`, `Удалить` после claim. Кнопка `Забрать всё` только при наличии доступных вложений; отдельное подтверждение при ошибках. Состояния: пусто, загрузка, нет сети, срок истёк, уже получено, новое письмо, массовая выдача. Использовать общий экран наград.

## 6. PostgreSQL и API
`mail_messages(id UUID PK, account_id, template_id, category, subject_key, body_params_json, created_at, expires_at, read_at, archived_at, status, source_type, source_id, period_key, UNIQUE(account_id,source_type,source_id,period_key))` (для уникальности nullable полей использовать частичный индекс/нормализованный source key); `mail_attachments(id,mail_id,resource_id,quantity,grant_id UNIQUE,claimed_at)`; `mail_delivery_outbox(id,account_id,event_id UNIQUE,mail_id,status,attempts,next_retry_at)`.

`GET /api/v1/mail?category=&cursor=`, `GET /api/v1/mail/unread-count`, `GET /api/v1/mail/{id}`, `POST /api/v1/mail/{id}/read`, `POST /api/v1/mail/{id}/claim`, `POST /api/v1/mail/claim-all`, `POST /api/v1/mail/{id}/archive`. События `mail_delivered`, `mail_read`, `mail_attachment_claimed`, `mail_expired`.

## Технические требования, единые для реализации
1. Все выдачи проводить в одной транзакции с существующим wallet/inventory ledger; `source_type`, `source_id`, `account_id`, `period_key`, `config_version`, `idempotency_key` обязательны. Уникальные индексы исключают повторный claim.
2. События публиковать через существующий event bus или transactional outbox: `event_id`, `account_id`, `event_type`, `occurred_at`, `payload`, `schema_version`; обработчики идемпотентны.
3. Клиент не может задавать размер награды, вероятность, завершённость задания, время или чужой `account_id`. GET возвращает серверное состояние и версию конфига; POST проверяет право и состояние.
4. Невыданные награды сохраняются в `pending_claims` или игровой почте; не теряются при сетевой ошибке, переполнении инвентаря или рестарте.
5. Админка: черновик → схема/проверка ссылок → симуляция → публикация версии → откат; audit log с actor, причиной и diff. Тестовые выдачи только в sandbox либо с отдельным разрешением и логом.
6. Автотесты: повтор POST, параллельный POST, неверный account_id, устаревший конфиг, переход через 06:00 МСК, рестарт, отсутствующий ассет, Android 9:16, плохая сеть, неактивный аккаунт.
7. API проектировать как `/api/v1/...`; названия адаптировать к фактическим роутам после аудита, не плодить несовместимые endpoints.
